# 추천 시스템 통합안 설계

> 작성: 2026-11-13 · 상태: **11/13 회의 확정안** (11/13 밤 개정: 요소별 점수를 공통 규칙과 교환비로 변경 → 3장)
> **챗봇(5장)은 아직 미완성이다.** 설계 방향만 정했고, 구현과 세부 규칙은 정해지지 않았다.
> 기준 코드: `feat/data-pipeline` (38a2a62, 11/10). 점수 계산은 `POST /recommend/v2`(`BE/app/scoring.py`)를 바탕으로 한다.
> 숫자는 모두 설정 파일에 모으고, 테스트 케이스로 조정한다.
> 구조도: `recommend_integrated_final.png`

---

## 한눈에 보기

| 단계 | 내용 |
|---|---|
| ① 입력 | 생활 프로필 (대학, 학과·학년, 우선순위, 조건 입력, 시간표) + 챗봇 대화 |
| ② 필터 | 대학 → 예산(여유 있음) → **챗봇 제외 조건** → 정보 없음 |
| ③ 점수 | **예산 · 이동 시간 · 면적** 3요소, 매물마다 절대 점수 0~100. 세 요소가 **같은 규칙**(기준 50점, 좋은 쪽 단위당 +5, 나쁜 쪽 단위당 −10)과 **교환비**(편도 10분 = 월 5만 원 = 2㎡)를 쓴다 |
| ④ 종합 | 1·2·3순위 가중치 0.55 / 0.30 / 0.15 |
| ⑤ 결과 | 추천 순위, 비추천 사유, 제외 목록과 사유, 계산 가정 |

- 계산은 전부 코드가 한다. LLM(챗봇)은 사용자의 말을 **확인 계획**(어떤 도구로 무엇을 확인할지)으로 바꾸는 일만 하고, 사용자가 계획을 승인한 뒤 코드가 실행한다. **챗봇은 아직 미완성이다(5장).**
- 지금 화면에 연결된 v3(카테고리 9개)는 이 통합안으로 교체한다.

## 1. 입력

### 1.1 생활 프로필 화면

| 섹션 | 입력 | 필수 | 비고 |
|---|---|---|---|
| 대학 선택 | 이대 / 서울과기대 / 고려대 / 서강대 | ✅ | 그 대학 매물만 추천 |
| 기본 정보 | 학과, 학년, 학과 건물 | ✅ | 이대는 학과 → 건물 예시표로 자동 채움. 학년은 받기만 함 |
| 우선순위 | 예산 / 이동 시간 / 면적 중 1·2순위 | ✅ | 3순위는 자동 |
| 조건 입력 | 유지비(월세+관리비) 상한 | ✅ | |
| | 보증금 상한 | 선택 | 없으면 보증금 필터 생략 |
| | 희망 통학 시간 (편도, 분) | ✅ | 도보 기준 |
| | 희망 면적 (㎡) | ✅ | |
| | 더 넓은 면적: 좋음 / 상관없음 / 싫음 | ✅ | 기본값 상관없음 |
| 시간표 | 요일, 시작·종료, 강의동 | 선택 | |
| 자주 가는 곳 | 장소, 주간 횟수 | 선택 | 데이터 준비 중 (계산에 안 씀) |

**삭제**: 별도 예산 섹션(조건 입력으로 합침), 강의동 방문 횟수, v3 카테고리 9개 카드와 기준별 질문(주간 통학 허용 시간, 공강 쉬는 시간, 1교시 여유).

### 1.2 API 요청 (`POST /recommend`)

v2 필드 이름을 그대로 쓰고, 면적과 챗봇 제외 조건을 더한다.

```json
{
  "university": "이화여자대학교",
  "department": "컴퓨터공학전공",
  "department_buildings": null,
  "grade": 2,
  "priorities": ["travel", "cost"],
  "budget_manwon": 75,
  "deposit_budget_manwon": 1000,
  "desired_commute_min": 15,
  "desired_area_m2": 20,
  "larger_area": "neutral",
  "timetable": [{"day": "월", "start": "09:00", "end": "10:15", "building": "ECC"}],
  "exclusions": []
}
```

- `priorities`: `travel` / `cost` / `area` 중 서로 다른 2개. v2의 `transit`(교통 편의성)은 삭제한다.
- `larger_area`: `like` / `neutral` / `dislike`
- `exclusions`: 사용자가 승인한 챗봇 확인 계획 (5장). 없으면 빈 목록.

## 2. 필터

순서대로 적용하고, 걸리면 제외하면서 사유를 남긴다.

| 순서 | 조건 | 제외 사유 예 |
|---|---|---|
| 1 | 요청한 대학의 매물만 | (목록에 넣지 않음) |
| 2 | 유지비 > 유지비 상한 + 10만 원 | "유지비가 상한보다 월 12만 원 많아서 제외" |
| 3 | 보증금 > 보증금 상한 × 1.2 (입력한 경우만) | "보증금이 상한보다 300만 원 많아서 제외" |
| 4 | 챗봇 제외 조건 (5장) | "주변 150m 안 술집 5곳" |
| 5 | 월세·관리비 또는 도보시간 정보 없음 | "도보시간 정보 없음: 공과대학" |

- 유지비가 상한과 상한 + 10만 원 사이인 매물은 남기고 **"예산 초과"**로 표시한다(`over_budget: true`).
- 면적 정보는 모든 매물에 있으므로 별도 조건이 없다.

## 3. 요소별 점수 (0~100, 절대 점수)

다른 매물에 따라 점수가 바뀌지 않는다.

### 3.1 공통 규칙

세 요소는 같은 규칙을 쓴다. 순위는 점수의 **차이**로만 정해지므로, 맞춰야 하는 것은 점수 수준이 아니라 **"같은 무게의 차이에 붙는 점수"**다. 요소마다 함수 모양이 다르면, 실제로 차이가 큰데도 함수 모양 때문에 점수 차이가 눌리거나(예: 희망 시간 안쪽이 평평한 구간) 반대로 작은 차이가 과하게 커지는(예: 희망 면적보다 조금 작을 때 급하게 떨어지는 구간) 문제가 생긴다.

```
점수 = 50 + 5 × (기준보다 좋은 쪽 단위 수)       기준보다 좋을 때
     = 50 − 10 × (기준보다 나쁜 쪽 단위 수)      기준보다 나쁠 때
     → 0~100으로 자름
```

- **기준**: 사용자가 입력한 값 (희망 통학 시간, 유지비 상한, 희망 면적). 기준을 딱 맞추면 어느 요소든 50점이다.
- **좋은 쪽은 단위당 +5점, 나쁜 쪽은 단위당 −10점**: 기준을 넘으면 두 배로 엄격해진다. 기준 안쪽에서도 좋을수록 꾸준히 점수가 오른다.
- **단위 (교환비)**: **편도 10분 = 월 5만 원 = 2㎡**. 같은 단위의 차이는 어느 요소에서나 같은 점수 차이를 만든다.

### 3.2 교환비를 정한 근거

4개 대학 매물 1,175개(11/13 기준 수집 데이터)로 "다른 조건이 같을 때 학교까지 1분, 면적 1㎡가 유지비(월세+관리비)를 얼마나 바꾸는가"를 회귀분석으로 구했다. 대학·매물 유형·보증금을 통제했다.

| 항목 | 시장 가격 (월) | 90% 신뢰구간 | 정한 단위 |
|---|---|---|---|
| 학교까지 도보 1분 | 약 0.43만 원 | 0.30 ~ 0.56만 원 | 10분 = 5만 원 (1분당 0.5만 원) |
| 면적 1㎡ | 약 2.4만 원 | 1.95 ~ 2.86만 원 | 2㎡ = 5만 원 (1㎡당 2.5만 원) |

- 도보는 강의동 4곳 평균 도보시간으로 쟀다. 면적 값은 대학마다 비슷했지만(1㎡당 1.4~3.2만 원), 도보 값은 고려대에서만 통계적으로 뚜렷했다.
- 시장 가격은 학생만이 아니라 모든 세입자를 대상으로 매겨진 값이라, 학생이 느끼는 통학의 무게보다 작을 수 있다. 이동 시간을 중요하게 여기는 학생은 1순위(가중치 0.55)로 반영한다.
- 데이터가 늘거나 테스트 케이스 결과에 따라 다시 정할 수 있다.

### 3.3 요소별 적용

| 요소 | 기준 | 좋은 쪽 (+5점/단위) | 나쁜 쪽 (−10점/단위) |
|---|---|---|---|
| 이동 시간 | 희망 통학 시간 (편도) | 희망보다 가까움 (10분 단위) | 희망보다 멂 (10분 단위) |
| 예산 | 유지비 상한 | 상한보다 쌈 (5만 원 단위) | 상한 초과, 여유 구간 (5만 원 단위) |
| 면적 | 희망 면적 | 넓은 면적 **좋음**: 넓을수록 +5점/2㎡ · **상관없음**: 50점 유지 · **싫음**: 넓을수록 −2.5점/2㎡ (완만한 감점) | 희망보다 좁음 (2㎡ 단위) |

**이동 시간 점수**는 v2 구조 그대로 세 부분을 합친다.

```
이동 시간 점수 = 0.4 × 학과 건물 + 0.4 × 자주 가는 곳 + 0.2 × 시간표
```

| 부분 | 편도 평균 | 기준 |
|---|---|---|
| 학과 건물 | 매물 ↔ 학과 건물 (여러 건물이면 평균) | 희망 통학 시간 |
| 자주 가는 곳 | 데이터 준비 중 → 비중을 나머지에 나눔 | (데이터가 생기면 정함) |
| 시간표 | 요일별 집 → 첫 수업, 마지막 수업 → 집 | 희망 통학 시간 |

입력이나 데이터가 없는 부분의 비중은 나머지에 비율대로 나눈다. 각 부분에 3.1 규칙을 적용한 다음 합친다.

### 3.4 예시

희망 통학 시간 15분, 유지비 상한 75만 원, 희망 면적 20㎡일 때:

| 이동 시간 | 0분 | 5분 | **15분** | 25분 | 35분 | 65분 이상 |
|---|---|---|---|---|---|---|
| 점수 | 57.5 | 55 | **50** | 40 | 30 | 0 |

| 유지비 | 25만 원 이하 | 45만 | 65만 | **75만** | 80만 | 85만 |
|---|---|---|---|---|---|---|
| 점수 | 100 | 80 | 60 | **50** | 40 | 30 |

| 면적 | 10㎡ 이하 | 16㎡ | 18㎡ | **20㎡** | 24㎡ | 30㎡ | 40㎡ |
|---|---|---|---|---|---|---|---|
| 좋음 | 0 | 30 | 40 | **50** | 60 | 75 | 100 |
| 상관없음 | 0 | 30 | 40 | **50** | 50 | 50 | 50 |
| 싫음 | 0 | 30 | 40 | **50** | 45 | 37.5 | 25 |

### 3.5 이전 함수와의 차이

| 요소 | 이전 (11/13 회의 직후) | 개정 |
|---|---|---|
| 이동 시간 | 희망 85점, 안쪽 거의 평평(0분 100점), 넘으면 10분마다 절반 | 희망 50점, 10분당 안쪽 +5 / 바깥 −10 |
| 예산 | 상한의 20% 이하 100점, 상한 0점, 초과 0점 | 상한 50점, 5만 원당 싸면 +5 / 초과면 −10 |
| 면적 | 희망 85점, 작으면 희망 면적의 20%마다 절반 | 희망 50점, 2㎡당 좁으면 −10, 넓으면 선택지대로 |

이전 함수를 실제 이대 매물(예산 필터 통과 155개)로 계산했을 때 확인된 문제:
- 희망 통학 시간을 40분으로 적은 학생은 실제 도보가 18~28분으로 10분 차이가 나는데도 이동 점수가 89~93점에 몰렸다(표준편차 2.5, 예산 점수 18.4). 도보 5분 차이가 1.9점, 월세 5만 원 차이가 8.3점이었다.
- 반대로 희망 면적보다 2㎡만 작아도 25점이 빠져, 월세 15만 원 차이와 같은 무게였다.

### 3.6 화면 표시

기준을 맞춘 매물이 50점이고 이동 점수는 0분이어도 57.5점이 최고라서, 점수를 그대로 보여주면 낮아 보일 수 있다. 계산에는 문제가 없다(순위는 점수 차이로만 정해진다). 화면에는 점수 대신 **기준 대비 값**("희망보다 5분 가까움", "예산보다 8만 원 쌈", "희망보다 2㎡ 넓음")을 보여주는 것을 권장한다.

## 4. 종합과 결과

### 4.1 종합 점수

```
종합 점수 = 0.55 × 1순위 점수 + 0.30 × 2순위 점수 + 0.15 × 3순위 점수
```
점수 높은 순 → 유지비 낮은 순 → 매물 ID 순.

### 4.2 결과 (v2 출력 구조)

| 항목 | 내용 |
|---|---|
| `ranked` | 순위, 종합 점수, 요소별 점수, 이동 시간 세부, 유지비, 면적, `over_budget` |
| `not_recommended` | 다른 순위 조합(6가지) 중 어디서든 상위 3위인데 지금은 상위 3위 밖인 매물, 최대 3개. 지금 1위와 비교해 가중 점수 차이가 가장 큰 요소를 사유로 쓴다 |
| `excluded` | 필터로 빠진 매물과 사유. 챗봇 조건으로 빠진 개수도 표시 |
| `assumptions` | 여유 금액, 희망 시간·면적과 넓은 면적 선택, 가중치(나눈 결과 포함), 승인된 챗봇 조건 |
| `notes` | 계산하지 못한 부분 등 안내 |

## 5. 챗봇 제외 조건 (미완성)

> **상태: 미완성.** 아래는 11/13에 정한 설계 방향이다. 구현되지 않았고, 도구별 기본값·화면·LLM 프롬프트 등 세부 규칙도 아직 정하지 않았다.
> 민경 로컬에 Gemini + LangGraph로 만든 임시 챗봇(`BE/app/agent/`, `POST /agent/chat`, 11/10)이 있으나 v3 추천(`recommend_v3`)을 호출하는 구조라, 통합안에 맞춰 다시 만들어야 한다.

### 5.1 흐름

```
사용자 말 → LLM이 확인 계획 작성 → 사용자 확인(승인·수정) → 코드가 도구로 매물마다 확인 → 제외 + 사유
```

- LLM은 **매물을 직접 판단하지 않는다.** 어떤 도구로 무엇을 확인할지만 정한다. 동네 사정을 모르는 LLM이 그럴듯하게 지어내는 것을 막기 위해서다.
- 도구로 확인할 수 없는 기호는 추측해서 빼지 않고 **"아직 확인할 수 없어요"**라고 안내한다(`unsupported`).
- 같은 계획이면 결과가 항상 같다.

### 5.2 확인 도구

| 도구 | 하는 일 | 데이터 |
|---|---|---|
| `nearby_count` | 매물 반경 N m 안 특정 장소 개수 | 카카오 장소 검색 (키워드·카테고리) |
| `nearest_distance` | 가장 가까운 특정 장소까지 거리 | 카카오 장소 검색 |
| `listing_field` | 매물 칸 조건 (면적, 보증금, 월세, 관리비) | 매물 CSV |

**추후 추가 예정**: 매물 설명 문구 확인("반지하", "엘리베이터" 등), 도로·소음 데이터, 경사도, 대중교통 시간 등.

### 5.3 확인 계획 형식

```json
{
  "source_text": "밤에 시끄러우면 잠을 못 자요",
  "conditions": [
    {
      "tool": "nearby_count",
      "label": "술집",
      "keywords": ["술집", "호프", "클럽"],
      "radius_m": 150,
      "exclude_if": {"op": ">", "value": 2}
    }
  ],
  "unsupported": [],
  "confirm_message": "주변 150m 안에 술집이 3곳 이상인 매물을 뺄게요. 괜찮으세요?"
}
```

### 5.4 규칙

- 사용자가 승인한 계획만 `exclusions`로 추천 요청에 넣는다.
- 매물 좌표가 없으면 장소 검색 도구를 실행할 수 없다. 그 매물은 빼지 않고, notes에 "좌표가 없어 확인하지 못한 매물 N개"로 남긴다.
- 같은 매물·도구·키워드·반경의 결과는 캐시한다. 카카오 결과 저장 정책은 확인이 필요하다.
- 추천 한 번에 카카오 호출 수에 상한을 둔다(초기값 500). 넘으면 조건을 줄이라고 안내한다.
- 조건 때문에 남은 매물이 없으면 제외된 개수를 보여주고, 조건을 풀 수 있게 한다.
- 자주 나오는 기호는 기본값을 둔다(예: 소음 → 술집·호프·클럽, 150m, 2곳 초과). LLM이 반경과 개수를 매번 다르게 정하는 것을 줄이기 위해서다.

## 8. 구현 순서

| 순서 | 작업 | LLM 필요 |
|---|---|---|
| 1 | BE 점수: 3장 공통 규칙(이동 시간·예산·면적), 여유 필터, transit 삭제 + 테스트 (3.4 예시표를 테스트로) | ✗ |
| 2 | BE API: `POST /recommend` 교체, v3 삭제 | ✗ |
| 3 | FE: 생활 프로필 재구성, 추천 결과 화면 | ✗ |
| 4 | 확인 도구 3개 + `exclusions` 실행 (계획 JSON을 직접 넣어 테스트) | ✗ |
| 5 | 챗봇 (미완성, 세부 설계 필요): 말 → 확인 계획, 확인 화면 | ✓ |

1~4는 LLM 없이 만들고 테스트할 수 있다. 5번은 4번의 계획 형식만 맞추면 병렬로 진행할 수 있다.

## 9. 남은 것과 한계

- **학과 → 건물 표**: 이대 예시 3개뿐이다. 다른 대학은 사용자가 건물을 고른다.
- **매물 좌표**: 레포의 PoC 매물 10개는 좌표가 비어 있다. 챗봇 장소 도구를 시연하려면 좌표가 있는 수집 데이터가 필요하다.
- **챗봇**: 미완성. 확인 도구의 기본값(소음 → 키워드·반경·개수 등), LLM 모델(Gemini/OpenRouter), 프롬프트, 확인 화면을 정해야 한다.
- **교환비**: 시장 가격으로 정한 값이라 학생이 느끼는 통학의 무게보다 작을 수 있다. "A가 B보다 위여야 한다" 형식의 테스트 케이스로 확인한다.
- **도로·소음**: 카카오 장소 검색으로는 확인할 수 없다. 추후 도구로 추가한다.
- **대중교통 시간**: 지금은 도보만 쓴다.
