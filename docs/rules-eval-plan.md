## 1. 챗봇 규칙 문서 구성

규칙마다 **번호(R-xx)**와 **좋은 답 / 나쁜 답 예시**를 단다. Syntitan이 "이 규칙을 지키는지" 시험하는 케이스를 만들고, 우리 평가 케이스도 규칙 번호로 묶어 어느 규칙이 약한지 보이게 한다.

| 장 | 내용 | 주요 규칙 |
|---|---|---|
| 1. 목적·범위 | 4개 대학(이대·고대·서강대·서울과기대) 인근 원룸·오피스텔 월세 추천. 데이터는 광고 매물(실제 거래 가능 여부 미확인) | 지원 대학 밖 지역은 범위 밖 |
| 2. 다루는 것 | 추천·비교·설명, 조건 변경·가정·되돌리기, 제외 조건 (시간표 사진은 읽지 않음 — 사용자가 직접 입력, 11/15) | — |
| 3. 입력 조건 | 필수: 학교, 학과 건물(또는 시간표), 1·2순위, 유지비 상한, 희망 통학 시간, 희망 면적. 학년은 묻지 않음. 넓은 면적은 말하지 않으면 '상관없음' | 평은 ㎡로 서버가 환산, 통학은 도보 기준 |
| 4. 추천 원칙 | 필터(유지비 +10만, 보증금 ×1.2), 기준 대비 점수, 1·2순위 비중 — **계산은 코드, 숫자는 설정값을 따른다** | 점수를 다시 매기지 않음 |
| 5. 제외 조건 | 도구로 확인되는 것만 뺀다. "~좋겠어"는 반대 조건을 제외로. **확인 질문 없이 바로 적용하고 '바뀐 것'을 먼저.** 0개가 남을 때만 적용하지 않고 되묻는다. 기본값 표(술집 30m 등) | 방음·곰팡이·채광·수압 등은 **추정 금지 → 현장 체크리스트** |
| 6. 되묻기 | 필수 조건이 없을 때만, 한 번에 2개까지 예시와 함께. 모호한 말은 묻지 않고 기본값을 적용한 뒤 밝힌다. 데이터에 없는 건물·학과는 고를 수 있는 목록 안내 | 지어내서 채우지 않음 |
| 7. 거절·범위 밖 | 계약·등기·사기 판단, 집주인, 투자·시세 전망, 매물 실재 보장, 지원하지 않는 지역, 주거와 무관한 질문 | 판단하지 않고 안내(예: 등기부등본·공인중개사·법률구조공단) |
| 8. 숫자 원칙 | 답에 쓰는 숫자는 계산 결과(facts)에 있는 것만. 점수보다 "희망보다 5분 가까움" 같은 기준 대비 값. 대중교통 시간은 말하지 않음(데이터가 도보) | 코드가 숫자 검증, 어긋나면 예비 문장 |
| 9. 응답 형식 | ① 바뀐 것 ② TOP 3 요약 ③ 예산 초과 표시 ④ 확인 못 한 것·현장 체크리스트 ⑤ 광고 매물 안내·원문 링크 | — |
| 10. 개인정보 | 조건·시간표는 생활 프로필에만 저장, 키·개인정보를 답에 넣지 않음 | — |

작성 원칙
- 판정할 수 있게 쓴다. "친절하게"가 아니라 "거절할 때 상담 기관을 하나 이상 안내한다"처럼.
- 기준값(10만 원, 1.2배, 30m)은 코드 설정과 같아야 한다. **문서 숫자 = 설정값을 확인하는 테스트**를 하나 둬서, 한쪽만 고치면 실패하게 한다.

## 2. 시스템 프롬프트로 옮기기

| 프롬프트 | 넣는 규칙 장 | 함께 넣는 것 |
|---|---|---|
| 조건 추출(EXTRACT) | 1·2·3·6·7 | 의도 목록(조건 변경·추천·가정·되돌리기·제외·제외 해제·설명·범위 밖), 추천 명세(설정값에서 자동 생성) |
| 제외 계획(PLAN) | 5·7 | `tool_catalog(props)`(도구·칸·기본값·현장 체크리스트), 예시 6개 |
| 설명(EXPLAIN) | 4·8·9 | facts(기준 대비 문장은 코드가 미리 만듦) |

- 문서 섹션을 코드(`app/agent/rules.py`)가 제목으로 찾아 프롬프트에 넣는다. 문서를 고치면 프롬프트도 같이 바뀐다.
- 프롬프트만 믿지 않는다. 코드 검증을 그대로 둔다.
  - 숫자 검증(facts에 없는 숫자 → 예비 문장)
  - 제외 계획 검증(칸·값·현장 확인 단어 차단)
  - 0개 남을 때 적용하지 않음

## 3. Syntitan Ready for Agent

OT 순서대로 진행한다: 매뉴얼·규정 문서 업로드 → 케이스 패키지 다운로드 → README의 실행 프롬프트로 팀 챗봇 시험 → 틀린 케이스 수정 후 재시험.

1. **업로드:** 규칙 문서만 올린다(PDF 또는 MD). 매물 CSV·키·`.env`는 올리지 않는다. 수집 데이터는 재배포하지 않는다는 원칙과 같다.
2. **케이스 받기:** 받은 패키지를 `BE/eval/syntitan/`에 보관하고 몇 개인지, 규칙별로 몇 개씩인지 기록한다.
3. **실행:** README 실행 프롬프트를 따르되, 가능하면 케이스를 우리 대화 턴 형식으로 바꿔 같은 실행기로 돌린다(결과표 형식 통일).
4. **1차 → 수정 → 2차:** 아래 5장과 같은 규칙으로 한다.
5. **기록:** 패키지 버전·업로드한 문서 버전(커밋)·통과 수를 결과표에 남긴다. 제출물과 발표에 쓴다.

## 4. 평가 세트 v2

### 4-1. 층

| 층 | 무엇을 보나 | LLM 호출 | 케이스 | 판정 |
|---|---|---|---|---|
| L1 코드 | 점수·필터·제외 도구·숫자 검증 | 없음 | pytest 157개(지금) | 자동, 변경마다 |
| L2 조건 추출 | 말 → 의도·조건 변경 | 1회/케이스 | 약 35 | 저장될 조건 비교(서버 검증 후) |
| L3 제외 계획 | 기호 → 확인 계획 | 1회/케이스 | 약 25 | 도구·칸·연산자 일치, 기준값 허용 범위, unsupported·onsite 목록 |
| L4 대화 턴 | 여러 턴 흐름 + 답 문장 | 2~3회/턴 | 약 15 | 상태 변화 + 문장 규칙(아래) |

### 4-2. 기존 케이스(32개) 변환

필드 이름을 바꾼다. `upkeep_max_manwon` → `budget_manwon`, `deposit_max_manwon` → `deposit_budget_manwon`, `first_category`·`categories` → `priorities`.

v3에만 있던 공강·1교시·주간 허용 통학 케이스는 둘 중 하나로 처리한다.
- "지금은 확인할 수 없어요"를 기대하는 케이스로 바꾼다.
- 뺀다.

### 4-3. 새로 만들 케이스 (규칙 번호로 묶음)

- **L2 조건 추출**
  - 1·2순위("통학이 제일 중요")
  - 평 → ㎡("6평")
  - 증감("예산 10만 올려")
  - 대중교통 시간 → 도보 안내
  - 학년은 묻지 않음
  - 조건 변경과 기호가 섞인 말
- **L3 제외 계획**
  - 시끄러움 → 술집 30m
  - "아주 조용" → 50m
  - 반지하·옥탑
  - 엘베 없는 고층
  - 근생 원룸
  - 편의점·빨래방 "있었으면" → 반대 조건
  - 방음·곰팡이·수압 → onsite만(조건 0개)
  - 큰 도로 소음 → unsupported
  - "보증금 500 넘으면 빼" → 제외가 아니라 조건 변경
  - 헬스장 → 칸이 있으면 amenity, 없으면 카카오
- **L4 대화 턴**
  - 필수 조건 되묻기(2개씩)
  - 거절 4종(계약·사기 판단, 범위 밖 지역, 시세 전망, 무관한 질문)
  - "바뀐 것"이 맨 앞
  - 0개가 남으면 적용하지 않고 되묻기
  - 제외 조건 지우기
  - 되돌리기
  - 지어낸 숫자 없음
  - 예산 초과 표시

### 4-4. L4 자동 판정 규칙

- **상태:** 의도, 저장된 조건, 적용된 제외 조건 수
- **문장:**
  - 제외를 적용한 턴의 답은 "바뀐 것:"으로 시작한다.
  - 답의 숫자는 facts에 있는 것만 쓴다(기존 검증 재사용).
  - 거절 답에는 안내처를 하나 이상 넣는다.
  - 금지 문구가 없어야 한다(예: "사기 아닙니다", "안전합니다", 지어낸 매물 이름).

### 4-5. 개발용 / 평가용 나누기

- 케이스의 약 25%를 **평가용(held-out)**으로 떼어 둔다. 수정할 때는 보지 않고 1차·2차 측정 때만 돌린다.
- Syntitan 케이스는 우리가 만든 게 아니라서 그 자체로 외부 평가 세트다. 수정 근거로 쓴 케이스는 표시해 둔다.

### 4-6. 통과 기준 (먼저 정하기 — 팀 결정)

| 층 | 제안 기준 |
|---|---|
| L2 조건 추출 | 90% 이상 |
| L3 제외 계획 | 85% 이상 |
| L4 거절·숫자·현장 추정 금지 | **100%** (안전·신뢰 규칙이라 하나도 틀리면 안 됨) |
| L4 그 밖 | 85% 이상 |
| Syntitan | 1차 대비 개선 + 80% 이상 |

## 5. 1차 → 수정 → 2차

1. **고정:** 모델(Gemini 3.1 flash-lite, temperature 0), 매물 데이터 버전, 케이스 파일. 결과표에 커밋 해시를 적는다.
2. **1차 실행:** 개발용 + 평가용 + Syntitan을 모두 돌린다.
3. **실패 분류:** 실패마다 하나를 고른다.
   - 프롬프트
   - 규칙 문서
   - 코드(검증·도구)
   - 케이스 기대값이 틀림
   - 데이터 없음

   마지막 두 가지는 통과 수에서 따로 표시한다.
4. **수정:** 개발용 실패만 보고 고친다. 평가용은 보지 않는다.
5. **2차 실행:** 같은 고정 조건으로 다시 돌리고, 전후 표를 만든다(예: "L3 25개 중 17 → 23, 평가용 6개 중 4 → 5").
6. **기록:** 결과표에 실패 이유 상위 3개와 고친 것을 남긴다. 발표·보고서의 "검증" 근거로 쓴다.

비용: 한 번 돌리면 LLM을 약 120회 부른다(L2 35 + L3 25 + L4 15턴 × 2~3). 실행 전에 Gemini 하루 한도를 확인하고, 한도 오류가 나면 이어서 돌릴 수 있게 실행기에 '이어 하기'를 둔다.

## 7. 정해야 할 것

1. 통과 기준(4-6장 제안 그대로 갈지)
2. 평가용 비율(25% 제안)
3. 거절 답의 안내처 목록(법률구조공단, 공인중개사, 등기부등본 확인 등)과 말투
4. Syntitan에 올릴 형식(MD/PDF)과 업로드 담당
5. "○○ 가까웠으면 좋겠어"의 기본 거리. 규칙 문서 R-508에 없다. 케이스(L3 e10·e11·e12)는 지금 250m 초과~600m 이하 사이 기준이면 통과로 두었다. 제안: 도보 5분, 400m 초과 제외
